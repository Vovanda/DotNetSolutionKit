# Секреты из Infisical или Vault

Генерируется с `-I` для [Infisical](https://infisical.com) или с `--Vault` для [HashiCorp Vault](https://www.vaultproject.io),
по умолчанию выключено. Флаг передаётся с `-M false` и каждому сервису, который генерируется позже и
читает секреты. Сказанное ниже верно для обоих; что у [Vault](#hashicorp-vault) иначе, описано в его разделе.

Сервис читает две папки проекта Infisical, общую и свою, и накладывает их поверх
остальной конфигурации. Код читает секрет как любую другую настройку: секрет с именем
`ConnectionStrings__DefaultConnection` - это `configuration.GetConnectionString("DefaultConnection")`.

Держите в хранилище и секреты, и обычные настройки. Значение там меняется без новой сборки и деплоя:
сервис перечитывает хранилище каждые `ReloadSeconds` (по умолчанию 300), и настройка, которую он
читает при каждом использовании, получает новое значение без перезапуска; см. [настройки](../architecture/settings.ru.md).

## Порядок

1. `appsettings.json`, `appsettings.<Environment>.json`, `appsettings.Secrets.json` в `Local`;
2. переменные окружения;
3. общая папка (по умолчанию `/`);
4. папка сервиса (`/orders` или `/sales_orders` для `Sales.Orders`).

Хранилище идёт последним, поэтому его значение побеждает всё, что зашито в образ, а папка сервиса
побеждает общую: сервис переопределяет общее значение, и общей папке не нужно знать, какие сервисы
существуют.

## Конфигурация

```json
"Infisical": {
  "ProjectId": "",
  "EnvironmentSlug": ""
}
```

`ProjectId` и `EnvironmentSlug` (`dev`, `staging`, `prod`) обязательны везде, кроме `Local`. У `HostUri`,
`SharedPath`, `ServicePath` и `Optional` есть значения по умолчанию. `SnapshotPath` пуст: пока он не
задан, снимок не хранится; см. ниже.

Машинная идентичность, `Infisical__ClientId` и `Infisical__ClientSecret`, берётся только из переменных
окружения. Файл в репозитории с ключом от хранилища вернул бы ту проблему, которую хранилище решает.

## HashiCorp Vault

С `--Vault` две папки - это два секрета key-value в движке KV версии 2: общий, по умолчанию `shared`, и
секрет сервиса, `orders` или `sales_orders` для `Sales.Orders`. Каждый ключ секрета - одна настройка, с
именем по тому же правилу.

```json
"Vault": {
  "Address": ""
}
```

`Address` обязателен везде, кроме `Local`. У `Mount` (`secret`), `SharedPath`, `ServicePath`, `SnapshotPath`
и `Optional` есть значения по умолчанию. Сервис входит по токену, `Vault__Token`, или через AppRole,
`Vault__RoleId` и `Vault__SecretId`, только из переменных окружения. Путь без секрета читается как
пустой, как пустая папка, поэтому сервису без своих секретов создавать секрет не нужно; отказ или
недоступный Vault обрабатываются, как описано ниже.

## Почему не переменные окружения

Без `-I` сервис берёт секреты из переменных окружения, и так же устроены значения по умолчанию этого
шаблона (`ConnectionStrings__DefaultConnection`, `RabbitMq__Password`). Это просто, но переменную
окружения может прочитать любой с доступом к хосту или контейнеру: `docker inspect` её печатает,
`/proc/<pid>/environ` её хранит, дамп процесса её содержит, а шаг CI, который печатает окружение,
публикует её в логе. Секрет в переменной окружения защищён не лучше, чем самый слабый путь на эту
машину.

С `-I` секреты лежат в хранилище и попадают в процесс только в памяти. Один секрет всё равно приходит
снаружи: машинная идентичность, с которой сервис читает хранилище. Ущерб от неё стоит держать малым:

- давайте идентичности доступ на чтение только к одному проекту и одному окружению;
- ротируйте её и отзывайте, когда хост выводится из работы.

<a id="why-infisical"></a>
## Почему Infisical

Задача: успешный взлом любого одного сервера не должен отдавать ключи от всей системы. Внутренний
API-ключ, ключ подписи токенов, учётные данные брокера лежат в окружении каждого сервера, который ими
пользуется; с хранилищем они лежат в одном месте с контролем доступа, а в окружении сервера есть только
идентичность, которая читает его долю.

Учётные данные брокера недооценивают чаще всего. Тот, у кого они есть, может публиковать команды и
события, которые сервисы выполняют как свои, с заголовками актора, в обход API, его проверок прав и
лога запросов. Украденный пароль от базы замечают, когда утекают данные; сообщения через брокер могут
менять данные незаметно.

Рассмотренные альтернативы:

- HashiCorp Vault. Зрелый и широко интегрированный, но его лицензия больше не open source, и он
  приносит сложность уровня enterprise команде, которой нужно хранилище секретов и настроек.
- OpenBao, open-source форк Vault под MPL-2.0. Проблемы с лицензией нет, сложность остаётся.
- Infisical. Open source, проще и заметно легче в эксплуатации, чем Vault, для команды, которая
  разворачивает его сама.

Шаблон читает хранилище через порт, поэтому позже можно добавить другое хранилище; см.
[дорожную карту](../roadmap.md).

<a id="when-the-store-is-unreachable"></a>
## Когда хранилище недоступно

В `Local` хранилище необязательно: разработчик работает от `appsettings.Secrets.json` без него. Во всех
остальных окружениях сервис отказывается стартовать без своих секретов. Сервис, который стартовал без строки
подключения или ключа, упадёт позже, на запросе, и дальше от причины.

Хранилище читается один раз, при старте. Секрет, изменённый в Infisical, применяется после перезапуска
сервиса.

### Снимок на случай аварии

Если задан `Infisical__SnapshotPath`, каждое успешное чтение копируется в этот файл, и старт, который не
может достучаться до хранилища, читает копию вместо отказа:

| Хранилище | Снимок | Сервис |
|---|---|---|
| отвечает | - | стартует на значениях хранилища и заменяет снимок |
| не отвечает | есть | стартует на снимке и пишет в лог предупреждение со временем его записи |
| не отвечает | нет | отказывается стартовать, как без снимка; вне `Local` |

Снимок содержит сами секреты, поэтому он выключен, пока его не включит тот, кто отвечает за сервис.
Снимок записывается с правами на чтение только для владельца, и ему место на томе, который монтирует
только этот сервис. В собственной файловой системе контейнера он исчезает вместе с контейнером и ничего
не защищает. Если снимок не удаётся записать, сервис не останавливается; старт пишет в лог причину,
поэтому отсутствие снимка обнаруживается до аварии, в которой он понадобится.

Чтобы поменять один фича-флаг, пока сервис работает на снимке, [закрепите его](feature-flags.ru.md#закрепление-флага)
в `features.json` вместо правки снимка.

## Тесты

`Common.Tests` покрывает порядок папок, необязательное и обязательное хранилище и снимок: сохраняется
после чтения, читается, когда хранилище не отвечает, доступен только владельцу на Linux, а неудачная
запись попадает в лог; хранилище при этом заменено заглушкой. С `--Vault` те же правила проверяются
через секцию `Vault`, а само хранилище Vault - на настоящем Vault в режиме разработки (`TEST_VAULT`) в
интеграционных тестах CI шаблона и сгенерированного решения.
